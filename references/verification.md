# 验证、安装与发布

## 分层验收

| 层 | 该层必须看到的证据 | 不能推出 |
| --- | --- | --- |
| 源码 | lint/typecheck、行为测试、预期入口/错误处理 | 打包结果正确 |
| 构建产物 | `exports`/`files` 实际存在、客户端外壳可加载、外部依赖能解析 | 运行 profile 已更新 |
| 组合/安装 | 独立 profile 安装、dump-config/插件管理结果、实际安装副本摘要、Host/Client 激活日志 | 用户点击路径成功 |
| 真实界面 | 从侧栏进入、执行目标动作，观察数据/网络/文件/媒体/会话结果与错误恢复 | 其他机器/版本可用 |
| 公开分发 | PR/CI/合并、Release 或包、全新 profile 安装、发布资产回读 | 目录上架或所有平台可用 |

优先使用独立测试 profile；在日用 profile 操作前保留配置与数据备份并明确目标。当前 DSH 的插件管理工具可用时，按其结构化结果判断是否已应用；否则用该版本官方 CLI。任何新客户端产物都要确认宿主重新加载了它。`file:` 依赖可能是安装时复制的包，源目录更新不代表 profile 内文件更新；`link:` 也不代表当前进程已重新执行代码。

## 故障定位顺序

1. 核对用户动作与现象，先看当前 profile、已安装版本和启动/浏览器日志。
2. Host 服务/工具失败：检查行配置、`Config`、注入服务、实例启动和 Remote provider。
3. 面板缺失：检查 Client package 的 `./client` export、`dsh.client` 元数据、模块外壳、实际 `require` 清单、Client `inject`、slot 注册与布局 id。
4. 面板存在而功能失败：检查目标请求、响应/错误、数据 owner、过期请求身份、草稿/会话引用、渲染状态和外部资源。
5. 更新后仍旧：比对源码、构建产物、profile 安装副本摘要与进程加载时间；必要时按宿主机制重载/重启，再重复原场景。
6. 若整个 Web boot 被一个插件阻塞，在**隔离 profile** 中逐个启动，保留精确错误与配置快照。恢复时也检查其他插件，不能把一个 panel 出现当成 profile 全部健康。

## 发布边界

只有用户明确授权发布才推送、创建 PR、合并或发布 Release。验证候选 commit 的 CI 与对应构建，公开安装走全新 profile；报告 `source merged`、`release available`、`clean install`、`live host` 分别是否成立。README 的安装命令要用同样方式实测。失败/未测明确写缺证据和复现步骤。
